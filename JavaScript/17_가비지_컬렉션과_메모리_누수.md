### 17. 가비지 컬렉션과 메모리 누수

<br>

#### 1. 자바스크립트는 왜 `free()`가 없을까?

---

- C 같은 언어는 개발자가 직접 메모리를 할당(`malloc`)하고 해제(`free`)해야 한다. 자바스크립트는 그럴 필요가 없다. 엔진이 **더 이상 도달할 수 없는(unreachable) 객체**를 알아서 찾아 메모리를 회수해주기 때문인데, 이 과정을 **가비지 컬렉션(Garbage Collection, GC)** 이라 부른다.
  > 찰떡 비유: 집주인이 알아서 치워주는 창고
- 창고(힙 메모리)에 물건(객체)을 넣는 건 자유지만, 안 쓰는 물건을 직접 내다 버릴 필요는 없다. 집주인(GC)이 정기적으로 창고를 돌면서 "지금 살고 있는 사람(루트, 예: 전역 객체·현재 실행 중인 함수의 지역 변수) 중 누구도 이 물건에 줄을 대고(참조하고) 있지 않다"고 판단되면 그 물건을 치운다. 반대로 말하면, **누군가 하나라도 참조하는 줄을 쥐고 있으면 절대 치워지지 않는다** — 메모리 누수는 대부분 "안 쓰는데 참조 줄만 살아있는" 상황에서 생긴다.
- 이 판단 기준을 **도달 가능성(reachability)** 이라 하고, 가장 기본적인 알고리즘이 **마크 앤 스윕(Mark-and-Sweep)** 이다.
  1. 루트에서 출발해 참조를 타고 갈 수 있는 모든 객체에 "마크"를 찍는다.
  2. 마크가 찍히지 않은(도달 불가능한) 객체를 전부 쓸어(sweep) 메모리를 회수한다.
- 여기서 흔히 하는 오해가 하나 있다 — **참조 카운팅(reference counting)** 과 헷갈리는 것이다. "참조하는 변수가 0개면 삭제"라는 방식은 서로가 서로를 참조하는 순환 참조(circular reference)를 못 지운다. 마크 앤 스윕은 "루트에서 도달 가능한가"만 보기 때문에 순환 참조가 있어도 둘 다 루트와 끊겨 있으면 정상적으로 수거된다.

#### 2. V8의 세대별 가비지 컬렉션(Generational GC)

---

- 크롬·Node.js가 쓰는 V8 엔진은 힙 전체를 매번 훑지 않는다. **"대부분의 객체는 어려서 죽는다(most objects die young)"** 는 경험칙(Generational Hypothesis)에 기반해 힙을 나이대별로 나눠 관리한다.
  > 찰떡 비유: 신입 사원 자리와 정규직 사무실
- 새로 만들어진 객체(함수 내부 임시 변수, 반복문의 중간 결과 등)는 대부분 **신입 사원 자리(Young Generation / New Space)** 에 앉는다. 회전율이 엄청 빨라서 인사팀(Scavenger, Minor GC)이 자주 들여다보며 이미 퇴사한(도달 불가능해진) 자리를 비운다. 반면 몇 번의 순환을 버티고 살아남은 객체(전역 캐시, 오래 유지되는 클래스 인스턴스 등)는 **정규직 사무실(Old Generation / Old Space)** 로 승진(promotion)한다. 이곳은 사람이 잘 안 바뀌니 청소(Major GC, Mark-Sweep-Compact)를 훨씬 뜨문뜨문, 대신 꼼꼼하게(마킹 → 압축 → 스윕) 진행한다.
- 신입 자리를 자주 비우는 이유는 간단하다 — 살아남는 객체가 적을수록 "복사해서 옮기는" 비용도 적기 때문에, 전체 힙이 아니라 **살아남은 객체 수에 비례하는 비용**만 지불하면 된다.
- Minor GC는 메인 스레드를 짧게만 멈추지만, Old Space를 정리하는 Major GC는 상대적으로 비용이 커서 **마킹 단계는 백그라운드 스레드에서 동시에(concurrent)** 처리하고, 실제로 메모리를 압축하는 부분만 메인 스레드를 잠깐 멈춘다. 이게 바로 대량의 객체를 오래 유지하는 코드(예: 전역 캐시에 데이터를 계속 쌓는 SPA)에서 스크롤이 순간적으로 끊기는 GC 프리즈 현상의 원인이다.

#### 3. 실무에서 자주 만나는 메모리 누수 패턴

---

- 가비지 컬렉터는 "도달 불가능한 것"만 치운다. 즉 **개발자가 실수로 참조 줄을 계속 쥐고 있으면 GC는 아무 잘못이 없어도 메모리가 계속 늘어난다.** 프론트엔드에서 실제로 자주 만나는 패턴 4가지다.

```javascript
/* ❌ [패턴 1] 의도치 않은 전역 변수 */
function leak() {
  // "use strict" 없이 var/let/const 없이 대입하면 전역 객체의 프로퍼티가 되어버려
  // 페이지가 살아있는 한 절대 GC되지 않는다.
  leakedData = new Array(1000000).fill("*");
}
```

```javascript
/* ❌ [패턴 2] 해제하지 않은 이벤트 리스너 + Detached DOM */
function attach() {
  const bigData = new Array(1000000).fill("*");
  const btn = document.querySelector(".my-btn");

  // 이 클로저는 bigData를 계속 참조한다.
  btn.addEventListener("click", () => console.log(bigData.length));
}
// 이후 btn을 DOM에서 제거해도(removeChild) 리스너를 떼지 않으면
// 리스너 자체가 btn과 bigData를 붙잡고 있어서 btn은 "화면에는 없지만 메모리에는 살아있는"
// Detached DOM 노드가 된다. 크롬 DevTools > Memory 스냅샷에서 "Detached"로 검색하면 바로 찾을 수 있다.
```

```javascript
/* ❌ [패턴 3] 정리되지 않는 타이머/구독 */
class Ticker {
  constructor(el) {
    this.el = el;
    // 컴포넌트가 사라져도 이 타이머는 this(=el 포함)를 계속 붙잡은 채 영원히 돈다.
    this.timer = setInterval(() => (this.el.textContent = Date.now()), 1000);
  }
}
```

```javascript
/* ✅ [해결] 생명주기가 끝날 때 참조를 확실히 끊는다 */
class Ticker {
  constructor(el) {
    this.el = el;
    this.timer = setInterval(() => (this.el.textContent = Date.now()), 1000);
  }
  destroy() {
    clearInterval(this.timer); // 타이머 해제
    this.el = null; // 참조 끊기
  }
}
// React 등 프레임워크라면 useEffect의 cleanup 함수, componentWillUnmount 시점에
// removeEventListener / clearInterval / unsubscribe를 짝지어 호출해야 한다.
```

#### 4. 약한 참조로 애초에 누수를 막기 — `WeakMap`·`WeakRef`

---

- 위 패턴들의 공통점은 "이 객체가 살아있는 한 나도 같이 살아있겠다"는 **강한 참조(strong reference)** 를 맺었다는 것이다. ES6 이후로는 **약한 참조(weak reference)** 를 만드는 도구가 표준에 들어왔다. 약한 참조는 "상대방이 사라지면 나도 자동으로 사라져도 괜찮다"는 뜻이다.
  > 찰떡 비유: 정식 세입자 계약 vs 메모 쪽지
- `Map`에 객체를 키로 넣는 건 **정식 세입자 계약**과 같다 — 세입자(키 객체)가 다른 곳에서 완전히 손을 뗐어도, 계약서(Map)가 남아있는 한 집주인(GC)은 그 사람을 내보내지 못한다. 반면 `WeakMap`은 냉장고에 붙여둔 **포스트잇 메모**다. 원본 객체가 다른 곳에서 사라지면 이 메모도 자동으로 같이 떨어져 나가 GC 대상이 된다. DOM 노드에 부가 정보를 붙이고 싶을 때 `WeakMap`을 쓰면, 노드가 화면에서 제거된 뒤 내가 따로 지우지 않아도 관련 데이터가 함께 청소된다.

```javascript
// ✅ DOM 노드별 메타데이터를 WeakMap으로 관리 — 노드가 사라지면 메타데이터도 같이 GC된다.
const metadata = new WeakMap();

function attachMeta(el, data) {
  metadata.set(el, data);
}

const el = document.querySelector(".card");
attachMeta(el, { clickCount: 0 });
// el을 DOM에서 제거하고 다른 참조도 없다면, metadata 안의 엔트리도 함께 사라진다.
// 일반 Map이었다면 metadata가 el을 붙잡고 있어 절대 GC되지 않는다.
```

- `WeakRef`는 한 걸음 더 나아가 객체 자체를 약하게 들고 있게 해준다. MDN은 사용에 신중할 것을 명시적으로 경고한다.
  > "Correct use of `WeakRef` takes careful thought, and it's best avoided if possible."
  > `WeakRef`를 올바르게 쓰려면 세심한 주의가 필요하며, 가능하면 피하는 것이 최선이다.
- GC가 **언제** 회수할지는 엔진 구현에 달려 있어 예측할 수 없기 때문에, "곧 사라지겠지"를 전제로 로직을 짜면 안 된다. 실무에서는 `WeakMap`/`WeakSet` 정도로 충분한 경우가 대부분이고, `WeakRef`·`FinalizationRegistry`는 캐시처럼 "있으면 좋고 없어도 그만"인 아주 제한적인 상황에서만 검토하는 게 안전하다.

#### 5. 정리

---

- GC는 **도달 불가능한 객체**만 치운다. 안 쓰는 객체를 계속 참조하고 있으면(전역 변수, 안 뗀 이벤트 리스너, 안 지운 타이머, 클로저에 붙잡힌 큰 데이터) 메모리 누수로 이어진다.
- V8은 **Generational GC**로 대부분 금방 죽는 젊은 객체(New Space, Scavenger)와 오래 살아남는 늙은 객체(Old Space, Mark-Sweep-Compact)를 다르게 관리해 비용을 줄인다.
- 생명주기가 끝나는 시점(컴포넌트 unmount, 이벤트 종료)에 리스너·타이머·구독을 반드시 정리하는 습관이 가장 확실한 예방책이다.
- DOM 노드처럼 "원본이 사라지면 나도 사라져도 되는" 부가 데이터는 `Map` 대신 `WeakMap`을 써서 GC가 알아서 정리하게 두는 것이 안전하다.
- 실제 누수 의심 시엔 크롬 DevTools의 Memory 탭에서 힙 스냅샷 두세 번을 비교(Comparison)해 계속 늘어나는 객체를 찾는 것이 가장 빠른 진단법이다.
