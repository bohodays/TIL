### 03. Rendering Mechanics: CSR의 폭포수를 넘어서는 RSC(서버 컴포넌트)의 혁명

<br>

#### 1. 1세대 패러다임, CSR (Client Side Rendering)

---

- 가장 먼저 우리가 순수 리액트(React)만으로 개발하던 도입 전의 `CSR`시절을 확인해보자. 여기서 'Client(클라이언트)'는 바로 여러분이 접속하는 크롬, 사파리 같은 '브라우저'를 의미한다. 즉, 브라우저가 화면을 그리는 모든 짐을 짊어졌던 시대이다.
  > 찰떡 비유: 조립되지 않은 이케아 가구 박스 사용자가 사이트 접속하면, 서버(가구 공장)는 완성된 가구가 아니라 텅 빈 상자(빈 HTML 파일)와 엄청나게 두꺼운 조립 설명서(거대한 자바스크립트 파일)만 덩그러니 던져준다. 브라우저(고객)는 그때부터 땀을 뻘뻘 흘리며 두꺼운 설명서를 다운로드해서 다 읽어본다. 다 읽고 났더니 "어? 나사(데이터)가 없네?"하고 다시 나사를 찾기 위해 서버에 API 요청을 보낸다. 나사가 도착하고 나서야 비로소 가구를 하나하나 조립(화면 렌더링)하기 시작한다.
- **CSR의 치명적인 고통: 폭포수(Waterfall) 현상**
  - 이 과정에서 사용자는 빈 상자만 쳐다보며, 하얀 화면과 로딩 스피너를 하염없이 바라봐야 했다. 구글 검색 봇(SEO) 역시 빈 페이지만 보고 "이 사이트는 내용이 없네"하고 떠나보내기 일쑤였다. 코드로 확인해보면 다음과 같다.

    ```jsx
    /* [Pain Point]: 초보자들이 가장 많이 겪는 CSR의 폭포수 지연 늪 */
    import { useState, useEffect } from "react";

    export default function ProductPage() {
      // 1. 초기 상태: 처음엔 데이터가 없으니 빈 그릇(null)을 만든다. 화면엔 아무것도 없다.
      const [data, setData] = useState(null);
      const [isLoading, setIsLoading] = useState(true);

      // 2. 폭포수 지연 시작!
      // 화면이 텅 빈 채로 한 번 켜진 직후(useEffect)에야 서버로 데이터를 가지러 떠난다.
      useEffect(() => {
        fetch("/api/products")
          .then((res) => res.json())
          .then((data) => {
            setData(data);
            setIsLoading(false); // 이 긴 통신이 끝나야 비로소 로딩 글자가 사라진다.
          });
      }, []);

      // 3. 데이터가 오기 전까지 사용자가 가장 먼저 마주하는 불친절한 화면
      if (isLoading) return <div>데이터를 가져오는 중입니다... 빙글빙글🌀</div>;

      // 4. 아주 긴 기다림 끝에 드디어 상품 이름이 화면에 그려진다.
      return <div>{data.name}</div>;
    }
    ```

#### 2. 2세대 과도기, SSR (Server Side Rendering)

---

- "브라우저가 너무 고생하니까, 서버에서 화면을 미리 좀 그려서 주자!" 이러한 문제를 해결하기 위해 등장한 것이 바로 `SSR`이다.
  > 찰떡 비유: 랩으로 꽁꽁 싸인 완성형 가구 이번엔 서버(가구 공장)의 전문가가 가구를 뼈대까지 다 조립해서 배달해 준다. 덕분에 브라우저(고객)는 상자를 열자마자 완성된 가구(미리 그려진 HTML 화면)를 즉시 눈으로 볼 수 있다. 하얀 로딩 화면의 고통이 사라진 것이다! 하지만 맹점이 있다. 가구에 흠집이 나지 않게 랩으로 꽁꽁 싸여 있어서, 눈으로 볼 수는 있지만 당장 서랍을 열거나 스위치를 누를 수(상호작용)는 없었다. 결국 기능을 활성화하려면, 랩을 벗기는 방법이 적힌 여전히 거대한 자바스크립트 설명서를 브라우저로 또 다운로드해야 한다는 근본적인 무거움은 해결하지 못한 상태였다.

#### 3. 3세대 혁명, RSC (React Server Components)

---

- 이제 우리가 배울 Next.js App Router가 제시하는 완전히 새로운 패러다임, RSC(서버 컴포넌트)의 시대가 열렸다. RSC는 아주 급진적인 철학을 가졌다. "서버에서 실행될 코드는 아예 브라우저로 보내지도 말자!"
  > 찰떡 비유: 최고급 장비로 시공 완료된 '붙박이 가구' 이제는 서버라는 가구 공장에서 전문가들이 최고급 장비(데이터베이스 연결)를 사용해 가구를 벽에 아예 완벽하게 설치해 버린다. 브라우저(고객)는 망치나 톱 같은 도구(JS 라이브러리)나 설명서를 전달받을 필요가 0%다. 그저 집에 들어와 이미 완벽하게 설치된 가구를 즉시 사용하기만 하면 된다.
- RSC 도입 후, 코드는 아래와 같다.

  ```jsx
  /* [Anatomy]: Next.js의 근본, RSC의 압도적인 간결함 */

  // 1. 주목! 파일 맨 위에 'use client'라는 글자가 없다.
  // 즉, 이 코드는 브라우저 밖으로 절대 나가지 않고 오직 서버 안에서만 실행된다.
  import db from "@/lib/db"; // 그래서 DB에 직접 연결해도 해킹당할 위험이 0%다.

  // 2. 컴포넌트 함수 자체에 async 하나만 툭 붙여준다. (useState, useEffect 완전 증발!)
  export default async function ProductPage() {
    // 3. 서버 내부 통신이다. 인터넷 네트워크를 타지 않으므로 폭포수 지연이 0초에 가깝다.
    // 데이터를 즉시 쏙 뽑아온다.
    const data = await db.product.findMany();

    // 4. 브라우저는 무거운 로직 다 빼고, 오직 이 '결과물(HTML 껍데기와 글자)'만 배달받는다!
    return (
      <div>
        {data.map((item) => (
          <div key={item.id}>{item.name}</div>
        ))}
      </div>
    );
  }
  ```

- **왜 RSC가 혁명일까? (Zero Bundle Size)**
  - 데이터베이스를 조회하는 무거운 로직이나, 어마어마한 용량의 외부 라이브러리를 설치해서 사용하더라도, 브라우저로 전송되는 자바스크립트 용량은 '0바이트'이다. 브라우저는 오직 서버가 연산해 낸 '결과물'만 낼름 받아먹기 때문에 앱이 깃털처럼 가벼워진다.
- [Deep Dive] RSC의 4단계 동작 시뮬레이션
  - 서버에서 브라우저까지 배달되는 과정은 아래의 4단계와 같다.

    **1\)요청 (Request)**: 사용자가 페이지 주소를 입력하고 접속한다.

    **2\)서버 실행 (Server Execution)**: Next.js 서버가 컴포넌트를 슥 훑고, 서버 내부에서 데이터베이스를 즉시 뒤져서 데이터를 가져온다.

    **3\)직렬화 (Serialization)**: 서버는 이 결과물을 무거운 자바스크립트 코드가 아니라, 'RSC Payload'라는 아주 가벼운 텍스트 지시서(JSON)로 압축한다. (예: "1번 구역에는 '아이폰', 2번 구역에는 '갤럭시' 글자만 넣어라")

    **4\)전송 및 반영 (Streaming)**: 이 가벼운 텍스트 지시서만 인터넷 망을 타고 브라우저로 날아간다. 브라우저는 지시서를 보자마자 1초 만에 화면을 완성한다.

#### 4. 하이브리드 모델과 `use client`의 비밀

---

- 여기서 아주 똑똑한 질문이 나올 수 있다. "그럼 화면에 '좋아요' 버튼을 누르면 숫자가 올라가야 하는데, 렌더링을 서버에서 다 끝내버리면 브라우저에서는 어떻게 클릭 이벤트를 작동시키나요?"
- 정답이다. 모든 것을 서버에서만 할 수는 없습니다. 사용자와 상호작용(`onClick` 이벤트, `useState` 상태 변화 등)이 필요한 요소는 브라우저(클라이언트)의 힘을 빌려야 한다. 그래서 Next.js는 RSC와 클라이언트 컴포넌트의 **하이브리드(Hybrid) 모델**을 채택했습니다.
  > 찰떡 비유: 고급 레스토링의 주방과 홀 직원
- **서버 컴포넌트 (주방)**: 보이지 않는 곳에서 무거운 장비(DB)로 요리(화면)를 완성한다. 홀(브라우저)로 절대 나가지 않는다.
- **클라이언트 컴포넌트 (홀 직원)**: 완성된 요리에 장식을 더하고, 손님(사용자)에게 다가가 직접 주문(클릭 이벤트)을 받고 대화를 나눈다.
- **출입증, `use client`**: Next.js는 기본적으로 내가 짠 모든 코드를 주방(서버)에 꽁꽁 가둬둔다. (보관 원칙) 하지만 "이 버튼은 클릭 기능이 필요해!"라고 판단되면, 해당 컴포넌트 파일 맨 위에 'use client'라는 라벨을 적어준다. 이것은 주방에서 홀로 나가기 위한 '출입증'이다.
- 이 출입증이 붙은 아주 작은 조각(버튼 등)만 브라우저로 전송된다. 무거운 짐은 서버에 다 던져두고, 클릭 같은 가벼운 기능만 브라우저로 보내는 최적화. "보낼 필요 없는 코드는 보내지 않는다"는 철학이 바로 Next.js가 미친 듯이 빠른 이유이다.
