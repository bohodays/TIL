### 01. Library vs Framework: 제어의 역전(IoC)과 Next.js의 탄생 배경

<br>

#### 1. Library의 한계: '빈 땅'의 건축가와 설정(Configuration) 지옥

---

- 과거 순수 리액트(Library)만으로 프로젝트를 구축하던 시절, 개발자는 마치 '빈 땅을 산 건축가'와 같았다.
  > 비유: 셀프 건축 시스템 리액트는 화면을 그리는 'UI'라는 벽돌만 제공할 뿐이다. 건물을 짓기 위해서는 기둥(라우터), 시멘트(상태 관리), 전기 배선(번들러) 등 수십 가지 도구를 개발자가 직접 선택하고 조립해야 했다.
- 이러한 무한한 자유는 곧 '설정(Configuration)의 늪'이라는 피로감으로 다가왔다. 페이지 이동 하나를 위해 우리가 감내해야 했던 React Router의 설정 코드를 살펴보자.

```jsx
/* [Pain Point]: React(Library) - 개발자가 모든 것을 수동으로 지시하는 방식 */
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";

function App() {
  return (
    // 1. 라우터 껍데기를 씌우고
    <BrowserRouter>
      <Routes>
        {/* 2. 어떤 URL에 어떤 화면을 보여줄지 개발자가 일일이 '매핑'한다. */}
        <Route path="/" element={<HomePage />} />
        <Route path="/about" element={<AboutPage />} />
      </Routes>
    </BrowserRouter>
  );
}
```

- 라이브러리 방식의 3대 페인 포인트 (Pain Points)
  - 높은 피로도: 필요한 외부 도구를 일일이 설치하고, 그 도구의 규칙을 새로 학습해야 한다.
  - 유지보수의 어려움: 페이지가 하나 늘어날 때마다 중앙 설정 파일(Entry Point)을 열어 라우팅 코드를 수정해야 하는 막노동이 발생한다.
  - 주도권의 피곤함: 코드를 '호출'하고 '제어'하는 모든 책임과 주도권이 개발자인 '나'에게 있다.

<br>

#### 2. Framework의 등장: '제어의 역전(IoC)'이라는 패러다임 시프트

---

- 이제 Next.js의 세계로 넘어오면 상황은 완전히 뒤바뀐다. 프레임워크는 빈 땅이 아니라 골조의 배관이 모두 갖춰진 '풀옵션 모델하우스'다. 이 거대한 변화를 관통하는 단 하나의 핵심 컴퓨터 공학 원리가 바로 제어의 역전(Inversion of Control, IoC)이다.
  > 핵심 개념: 제어의 역전 (IoC) 이란? 쉽게 말해 '주도권이 넘어갔다'는 뜻이다. 과거에는 내 코드가 중심에 있고 내가 도구들을 호출했다면, 이제는 프레임워크(Next.js)가 뼈대를 잡고 있고 내 코드는 그저 부품처럼 끼워져 '호출 당하는' 구조가 된 것이다.
- 비유 : Next.js 호텔 시스템
  - Next.js에서 `app` 폴더는 호텔의 로비이고, 그 안의 폴더들은 방이다. 우리가 만들 `page.tsx`는 그 방 안의 메인 공간이다. "101호 문을 열면 침대를 보여줘"라고 지시서를 쓸 필요 없이, 101호 문을 여는 순간 프레임워크가 알아서 방을 보여준다.

  ```jsx
      /* [Solution]: Next.js(Framework) - 설정 대신 '관습'을 따르는 마법 */

      // 1. app/page.tsx (메인 화면)
      export default function HomePage() {
      return <h1>🏨 호텔 로비 (/)</h1>;
      }

      // 2. app/about/page.tsx (About 화면)
      export default function AboutPage() {
      // 라우터 설정 코드 없이, 폴더와 파일 생성만으로 '/about' 주소가 연결된다.
      return <h1>ℹ️ 101호 객실 (/about)</h1>;
      }
  ```

- **제어의 역전이 가져온 결과**
  - 개발자는 export default를 통해 완성된 요리(컴포넌트)를 주방장(Next.js)에게 건네주기만 하면 된다. 렌더링을 언제, 어떻게 할 것인지는 전적으로 프레임워크가 제어한다.

<br>

#### 3. 결론: 설정(Configuration)보다 관습(Convention)

---

- Next.js를 배운다는 것은 단순한 문법 공부가 아니다. `설정보다 관습을 따른다`는 프레임워크의 철학에 동의하는 과정이다.
  - **Library (React)**: 내가 도구를 조종한다. (자유도 ⬆️, 설정 피로도 ⬆️)
  - **Framework (Next.js)**: 프레임워크가 나를 조종한다. 나는 규칙만 지킨다. (생산성 ⬆️, 비즈니스 로직 집중 ⬆️)
- 프레임워크가 닦아놓은 고속도로의 규칙만 잘 지켜주면, 내부 엔진이 복잡한 배선과 라우팅 최적화를 완벽하게 처리해준다. 특히, 우리가 앞으로 다룰 이 app 폴더 기반의 아키텍처는 Next.js 15의 가장 강력하고 완벽한 최신 표준인 'App Router' 방식이다.
- 이제 우리는 "어떻게 연결할까?"라는 낡은 인프라 고민에서 완벽히 해방되어, "어떤 화면을 보여줄까?"라는 서비스의 본질에만 100% 집중할 수 있게 되었다.
