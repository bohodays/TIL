### 03. Hydration Deep Dive 정적 HTML에 자바스크립트 생명력을 불어넣는 마법과 Mismatch 해결법

<br>

#### 1. 도대체 '하이드레이션'이 뭔가요?

---

- 영어 단어가 낯설게 느껴질 수 있지만, 원리는 아주 간단하다. Hydration의 사전적 의미는 '수분 공급'이다.
  > 찰떡 비유:: 컵라면 속 바짝 말린 건조 채소
- 우리가 흔히 먹는 컵라면이나 인스턴스 국에 들어있는 **건조 채소**를 떠올려 보자. 모양은 분명 파, 버섯, 고추인데 바짝 말라서(Dry) 씹어 먹을 수도 없고 맛도 나지 않는다. 이것이 바로 서버에서 갓 도착한 **정적인 HTML**의 상태이다.
- 이 딱딱한 채소를 먹을 수 있게 만들려면 무엇 필요할까? 바로 **뜨거운 물**이다. 바짝 마른 정적인 HTML(건조 채소)에 **자바스크립트(뜨거운 물)**를 쫘악 부어주면, 채소가 촉촉해지며 생상하게 살아나듯 죽어있던 HTML이 클릭도 되고 입력도 되는 살아있는 앱으로 변신한다.
- 이렇게 수분(자바스크립트)을 공급하여 생명력을 띠게 만드는 과정을 개발 용어로 **하이드레이션**이라고 부른다.

<br>

#### 2. 서버와 브라우저의 릴레이 협동 (포크와 나이프)

---

- 이 과정을 완벽하게 이해하기 위해, 지난 시간에 배웠던 렌더링 방식들과 연결해서 큰 그림을 그려보자.
- **CSR (이케아 가구)**: 텅 빈 방에 덜렁 도착한 조립 설명서. 브라우저가 처음부터 끝까지 다 조립해야 해서 초기 로딩이 너무 느리다.
- **SSR (고급 스테이크 하우스)**: 주방장(서버)이 주방에서 스테이크를 완벽하게 구워서 접시에 담아 내어준다. 우리는 자리에 앉자마자 맛있는 음식을 눈으로 볼 수 있다!
- 여기에 문제가 있다. 눈앞에 스테이크(완성된 HTML)는 있는데, 썰어 먹을 포크와 나이프(자바스크립트/이벤트 리스너)가 도착하지 않았다! 상호작용을 할 수 없는 답답한 찰나의 순간이 발생한다.
- 이때 웨이터(브라우저)가 달려와 여러분의 손에 포크와 나이프를 착착 쥐여주는 과정, 뼈대에 알맞게 이벤트 리스너를 끼워 맞춰 생명력을 불어넣는 과정! 이것이 바로 `하이드레이션`이다.

<br>

#### 3. Next.js의 필살기, '부분 하이드레이션'

---

- 모든 프레임워크가 하이드레이션을 똑같이 하는 것이 아니다. 과거에는 아주 작은 '좋아요' 버튼하나를 살리기 위해, 페이지 전체에 거대한 양의 물(자바스크립트)을 들이부어야 했을만큼 비효율적이었다. 하지만 Next.js는 **부분 하이드레이션(Partial Hydration)** 이라는 놀라운 기술을 사용한다.
  > 찰떡 비유: 똑똑한 스마트 스프링클러
- 마당에 물을 줄 때, 생명이 없는 돌멩이(정적인 텍스트)에는 물을 주지 않고, 오직 생명이 피어날 꽃(버튼, 입력창 등)에만 정확하게 물을 쏘아주는 스마트 스프링클러와 같다.
- **RSC(서버 컴포넌트)** 는 영원히 변하지 않는 돌멩이이므로 아에 하이드레이션 대상에서 제외된다. 오직 `use client` 출입증이 붙은 **클라이언트 컴포넌트(꽃)** 만 콕 집어서 물을 준다. 덕분에 Next.js 앱은 획기적으로 가볍고 빠르다.

<br>

#### 4. 전 세계 개발자의 악몽, Hydration Mismatch

---

- 이 정교한 협동 작업에는 아주 까다롭고 무서운 규칙이 하나 숨어있다. **서버(주방장)가 내어준 요리의 모양과, 브라우저(웨이터)가 예상한 요리의 모양이 단 1밀리미터, 1픽셀도 틀리지 않고 완벽하게 일치해야한다!"** 는 것이다.
- 만약 주방장은 스테이크를 보냈는데, 웨이터가 수프인 줄 알고 숟가락을 가져다준다면 식당은 난장판이 될 것이다. 리액트도 마찬가지이다. 서버에서 그린 그림과 브라우저가 그리려는 그림이 다르면, 리액트는 혼란에 빠져 기존 HTML을 다 부수고 처음부터 다시 그리는 비효율적인 행동을 하며 빨간 에러를 토해낸다. 이것이 바로 **Hydration Mismatch(불일치) 현상** 이다.
- 참고로 **Next.js 15** 로 넘어오면서 과거에는 에러 메시지가 정말 불친절해서 '악몽'같았지만 서버와 브라우저의 차이를 마치 틀린 그림 찾기 게임처럼 아주 명확하게 비교해서 보여준다. 덕분에 원인을 찾기 훨씬 쉬워졌지만 여전히 성능에는 치명적이니 꼭 해결해야만 한다.
- 무의식적으로 발생하는 실수는 다음과 같다.

```jsx
/* ❌ [안티 패턴] Mismatch를 유발하는 전형적인 초보자의 실수 */
export default function TimeDisplay() {
  // 🚨 실수 1: 시간 (Time)
  // 서버가 HTML을 만든 시간(10:00:00)과,
  // 인터넷 선을 타고 브라우저에 도착해 JS가 실행된 시간(10:00:01)은 영원히 다르다!
  const time = new Date().toLocaleTimeString();

  // 🚨 실수 2: 랜덤 값 (Random)
  // 서버가 굴린 주사위 값(0.12)과 브라우저가 굴린 주사위 값(0.99)은 일치할 수 없다!
  const randomId = Math.random();

  return (
    <div id={randomId.toString()}>
      <h1>현재 시각</h1>
      <p>{time}</p>

      {/* 🚨 실수 3: 잘못된 HTML 구조 (Invalid Nesting) */}
      <p>
        {/* p태그(문단) 안에는 div태그(구역)가 들어갈 수 없다. (HTML 문법 위반) */}
        {/* 브라우저가 이걸 몰래 고치려고 시도하다가 리액트에게 딱 걸려서 에러가 난다. */}
        <div>Description</div>
      </p>
    </div>
  );
}
```

#### 5. Mismatch를 우아하게 해결하는 두 가지 마법

---

- 이 무서운 에러를 해결하려면 **완벽하게 동기화** 하거나 **알고도 눈감아주기** 스킬을 사용해야 한다.

```jsx
/* ✅ [해결책] Mismatch를 해결하는 올바른 패턴의 정석 */
"use client";
import { useState, useEffect } from "react";

export default function SafeTimeDisplay() {
  // ✨ 패턴 1: Two-Pass Rendering (강제 일치시키기)
  // 초기값을 아예 비워둔다(null). 서버도 "없음!", 브라우저의 첫 모습도 "없음!"으로 일치시킨다.
  const [time, setTime] = (useState < string) | (null > null);

  useEffect(() => {
    // useEffect는 '하이드레이션(수분 공급)이 완전히 끝난 후'에만 실행된다.
    // 즉, "포크와 나이프가 다 지급된 후(오직 브라우저에서만!)" 시간을 세팅한다.
    setTime(new Date().toLocaleTimeString());
  }, []);

  return (
    <div>
      <h1>현재 시각</h1>

      {/* 해결 방법 1: 로딩 중 처리 (안전함의 정석) */}
      {time ? <p>{time}</p> : <p>Loading...</p>}

      {/* ✨ 패턴 2: suppressHydrationWarning (치트키: 알고도 눈감아주기) */}
      {/* "리액트야, 서버랑 브라우저 시간 다른 거 나도 알아. 에러 띄우지 말고 그냥 브라우저 값으로 덮어씌워!" */}
      {/* ⚠️ 주의: 텍스트가 다를 때만 써야지, 태그 구조 자체가 다를 때 쓰면 앱이 망가진다! */}
      <p suppressHydrationWarning>{new Date().toLocaleTimeString()}</p>
    </div>
  );
}
```

- **패턴 1 (Two-Pass Rendering)**: 서버와 브라우저의 첫인상을 강제로 일치시키고, 브라우저가 준비된 이후(useEffect)에 데이터를 넣는 가장 안전한 정석이다.
- **패턴 2 (suppressHydrationWarning)**: 어쩔 수 없이 텍스트 차이가 날 때 사용하는 리액트 전용 치트키이다.
