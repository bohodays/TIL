### 01. staleTime과 gcTime

<br>

#### 1. TanStack Query는 왜 "요청"이 아니라 "캐시"를 관리할까?

---

- TanStack Query(구 React Query)를 처음 쓰면 `useQuery`가 알아서 로딩·에러·캐싱을 다 해주니 편리하다고만 느끼기 쉽다. 하지만 실무에서 "분명 데이터가 캐시에 있는데 왜 화면 진입할 때마다 다시 요청을 쏘지?", "탭을 옮겼다 왔더니 로딩이 다시 뜨네?" 같은 삽질을 하는 순간, 두 개의 타이머를 반드시 구분해서 알아야 한다는 걸 깨닫게 된다. 바로 **`staleTime`** 과 **`gcTime`** 이다.
  > 찰떡 비유: 냉장고 속 반찬의 "유통기한"과 "폐기 시점"
- 냉장고에 반찬을 넣어두면 두 개의 서로 다른 시점이 존재한다. 하나는 **"언제부터 맛이 변하기 시작하는가(유통기한, staleTime)"**, 다른 하나는 **"언제 아예 버려야 하는가(폐기 시점, gcTime)"**. 유통기한이 지났다고 반찬이 사라지는 건 아니다 — 꺼내 먹을 수는 있지만(캐시에서 즉시 보여주지만), 상했을 수 있으니 일단 새로 사와서 바꿔치기(백그라운드 리페치)한다. 반면 아무도 그 반찬을 꺼내 먹지 않은 채로(컴포넌트가 전부 언마운트된 채로) 폐기 시점이 지나면, 유통기한과 무관하게 냉장고에서 통째로 치워버린다.

<br>

#### 2. `staleTime` — 데이터가 "신선한(fresh)" 상태로 남는 시간

---

- 공식 문서는 `staleTime`을 이렇게 설명한다.
  > "The duration until a query transitions from fresh to stale."
  > 쿼리가 fresh(신선) 상태에서 stale(오래됨) 상태로 바뀌기까지 걸리는 시간이다.
- 쿼리가 **fresh** 상태인 동안에는 같은 `queryKey`로 아무리 많은 컴포넌트가 마운트돼도 **네트워크 요청 없이 캐시된 데이터만 그대로 반환**한다. 반대로 **stale** 상태가 되면, 캐시된 데이터는 여전히 화면에 즉시 보여주되(그래서 로딩 스피너가 안 뜬다) 지정된 트리거(컴포넌트 마운트, 윈도우 포커스, 네트워크 재연결 등)가 발생하면 **백그라운드에서 조용히 리페치**한다.
- 기본값은 `0`이다. 즉 **기본 설정에서는 데이터가 도착하는 즉시 stale이 된다.** "그럼 캐싱이 의미가 없는 거 아닌가?" 싶을 수 있지만, stale이어도 캐시 자체는 여전히 살아있어서 즉시 보여줄 수 있다는 점이 핵심이다 — 다만 신뢰할 수 있는 최신 데이터인지 보장이 없으니 트리거가 걸릴 때마다 다시 확인하러 가는 것뿐이다.

```jsx
// ❌ staleTime 기본값(0)이면, 같은 화면을 재방문할 때마다 매번 백그라운드 요청이 나간다.
useQuery({ queryKey: ["todos"], queryFn: fetchTodos });

// ✅ 자주 안 바뀌는 데이터(예: 카테고리 목록)라면 staleTime을 넉넉히 주어
// 불필요한 재요청을 줄인다.
useQuery({
  queryKey: ["categories"],
  queryFn: fetchCategories,
  staleTime: 1000 * 60 * 10, // 10분 동안은 fresh로 취급 → 재방문해도 재요청 안 함
});
```

#### 3. `gcTime` — 아무도 안 쓰는 캐시를 메모리에서 치우는 시간

---

- `gcTime`은 v5에서 붙은 이름이고, v4까지는 `cacheTime`이라 불렸다. TanStack 팀이 이름을 바꾼 이유를 GitHub 이슈에서 이렇게 설명한다.
  > "gc" refers to "garbage collect" time — a bit more technical, but also a well known abbreviation in computer science.
  > "gc"는 "garbage collect(가비지 컬렉션)"의 줄임말이며, 조금 더 기술적이긴 하지만 컴퓨터 과학에서 널리 알려진 약어다.
- 어떤 `queryKey`를 구독하는 `useQuery` 인스턴스가 **하나도 남지 않으면(=옵저버 0개)**, 그 쿼리는 "비활성(inactive)" 상태가 되고 그 순간부터 `gcTime` 타이머가 카운트다운을 시작한다. 타이머가 끝날 때까지 아무도 다시 구독하지 않으면 캐시에서 완전히 삭제된다. 기본값은 `1000 * 60 * 5`, 즉 **5분**이다.
- 여기서 자주 하는 오해가 "컴포넌트가 언마운트되면 바로 캐시가 사라진다"는 것이다. 실제로는 그렇지 않다 — **비활성 상태가 되어도 `gcTime` 동안은 캐시가 살아있어서**, 그 시간 안에 같은 페이지로 다시 돌아오면 네트워크 요청 없이(또는 `staleTime`이 지났다면 백그라운드 리페치와 함께) 즉시 이전 데이터를 보여줄 수 있다.

```jsx
// SSR 환경(Next.js 등)에서는 서버에서 만든 쿼리 캐시가 응답을 보내는 즉시 필요 없어지므로,
// 기본 5분을 기다릴 필요 없이 gcTime을 짧게 줄이는 것이 메모리 관리에 유리하다.
useQuery({
  queryKey: ["product", id],
  queryFn: () => fetchProduct(id),
  gcTime: 0, // 옵저버가 사라지는 즉시 가비지 컬렉션 대상으로
});
```

#### 4. 하나의 타임라인으로 같이 보기

---

- 두 타이머는 서로 다른 기준으로 흘러가기 때문에, 실제 화면 전환 시나리오에 겹쳐놓고 봐야 헷갈리지 않는다. `staleTime: 0`, `gcTime: 5분`(둘 다 기본값)인 `['todos']` 쿼리를 예로 들면 공식 문서의 캐싱 가이드는 다음과 같은 흐름을 보여준다.

  1. `['todos']`를 구독하는 첫 `useQuery` 인스턴스가 마운트된다 → 캐시에 없으므로 네트워크 요청 → 결과를 캐시에 저장.
  2. 두 번째 인스턴스가 같은 키로 마운트된다 → 캐시된 데이터를 즉시 반환하면서(이미 stale이므로) 동시에 백그라운드 리페치를 트리거한다.
  3. 두 인스턴스가 모두 언마운트된다 → 옵저버 0개, 쿼리가 **inactive**로 전환되며 `gcTime`(5분) 카운트다운 시작.
  4. 5분 안에 세 번째 인스턴스가 다시 마운트되면 → 캐시된 데이터를 즉시 반환(로딩 스피너 없음) + 백그라운드 리페치. 타이머는 리셋된다.
  5. 5분 동안 아무도 구독하지 않으면 → 캐시에서 완전히 삭제(garbage collected). 이후 다시 마운트되면 처음부터 새로 요청해야 한다.

- 즉 **`staleTime`은 "네트워크 요청을 다시 보낼지"를 결정하고, `gcTime`은 "메모리에서 데이터를 아예 지울지"를 결정한다** — 서로 다른 축의 설정이라 한쪽만 조정해서는 원하는 동작이 안 나올 때가 많다.

<br>

#### 5. 실전에서 값을 정하는 기준

---

- **`staleTime`을 늘려야 하는 경우**: 사용자 프로필, 카테고리/코드성 데이터처럼 실시간성이 중요하지 않은 데이터. 탭을 오갈 때마다 스피너 없이 즉시 보여주고 싶다면 `staleTime`부터 늘리는 게 정답이다. `Infinity`로 주면 명시적으로 `invalidateQueries`를 호출하기 전까지 절대 재요청하지 않는다.
- **`gcTime`을 줄여야 하는 경우**: 메모리 사용량이 민감한 모바일 웹, 혹은 SSR에서 요청마다 새 `QueryClient`를 만드는 구조라면 굳이 5분씩 인메모리에 들고 있을 이유가 없다.
- **흔한 함정**: `gcTime`을 `staleTime`보다 짧게 주는 조합이다. 데이터가 fresh하다고 믿고 있는 동안 캐시 자체가 먼저 청소돼버려서, 재마운트 시 캐시가 있을 거라 기대했는데 처음부터 다시 로딩 스피너가 뜨는 원인이 된다. 일반적으로 **`gcTime`은 `staleTime`보다 같거나 길게** 설정하는 것이 안전하다.
