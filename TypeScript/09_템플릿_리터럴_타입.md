### 09. 템플릿 리터럴 타입 (Template Literal Types)

<br>

#### 1. 템플릿 리터럴 타입이란

---

- JS의 템플릿 리터럴(`` `hello ${name}` ``)과 똑같은 문법을 **타입 레벨**에서 쓰는 기능 (TS 4.1)
- 문자열 리터럴 타입들을 이어 붙여서 "이런 패턴의 문자열만 허용한다"는 새 리터럴 타입을 만들어냄

```typescript
type World = "world";
type Greeting = `hello ${World}`;
// type Greeting = "hello world"
```

- 값이 아니라 타입을 만드는 문법이라는 점이 핵심 — 런타임에는 아무 영향이 없고, 컴파일 타임에 문자열의 "모양"을 검사하는 용도

<br>

#### 2. 유니온이 들어가면 조합 폭발이 일어남

---

- 템플릿 리터럴 자리에 유니온 타입을 넣으면, 가능한 모든 조합이 **카테시안 곱**으로 펼쳐져서 새로운 유니온이 됨

```typescript
type EmailLocaleIDs = "welcome_email" | "email_heading";
type FooterLocaleIDs = "footer_title" | "footer_sendoff";

type AllLocaleIDs = `${EmailLocaleIDs | FooterLocaleIDs}_id`;
// "welcome_email_id" | "email_heading_id" | "footer_title_id" | "footer_sendoff_id"

type Lang = "en" | "ja" | "pt";
type LocaleMessageIDs = `${Lang}_${AllLocaleIDs}`;
// "en_welcome_email_id" | "en_email_heading_id" | ... 총 3 × 4 = 12개 조합
```

- 08번 글의 [[08_조건부_타입과_infer.md#3. 분산 조건부 타입|분산 조건부 타입]]과 비슷하게, "유니온 하나하나에 대해 따로 계산하고 다시 합친다"는 감각으로 이해하면 편함
- 다만 조합 수가 기하급수적으로 늘어나므로, 유니온을 여러 개 겹쳐 쓰면 타입 체크 속도가 느려지거나 IDE가 버벅일 수 있음 — 조합 가짓수가 감당 가능한 범위(라우트 경로, 이벤트 이름, CSS 프로퍼티처럼 후보가 유한한 경우)일 때 쓰는 게 안전함

<br>

#### 3. 내장 문자열 조작 유틸리티 타입

---

- 컴파일러에 내장된 4가지 유틸리티로 리터럴 문자열의 대소문자를 타입 레벨에서 변환할 수 있음

```typescript
type Greeting = "Hello, world";

type ShoutyGreeting = Uppercase<Greeting>; // "HELLO, WORLD"
type QuietGreeting = Lowercase<Greeting>; // "hello, world"
type Capitalized = Capitalize<"hello world">; // "Hello world"
type Uncapitalized = Uncapitalize<"HELLO WORLD">; // "hELLO WORLD"
```

- 별도 라이브러리 없이 컴파일러 내장 기능으로 처리되기 때문에 성능 부담이 없음
- 뒤에 나오는 키 리매핑에서 `getName`, `onClick`처럼 프로퍼티명 첫 글자를 대문자로 바꿔야 할 때 실전에서 자주 쓰임

<br>

#### 4. infer와 결합해서 문자열 패턴에서 타입 추출하기

---

- 08번 글에서 다룬 `infer`를 템플릿 리터럴 타입 안에서도 그대로 쓸 수 있음 — 문자열을 패턴에 맞춰 쪼갠 뒤 특정 부분만 뽑아내는 용도
- 이벤트 이름(`"firstNameChanged"`)에서 프로퍼티 이름(`"firstName"`)만 추출하는 예시

```typescript
type PropEventSource<Type> = {
  on<Key extends string & keyof Type>(
    eventName: `${Key}Changed`,
    callback: (newValue: Type[Key]) => void
  ): void;
};

declare function makeWatchedObject<Type>(
  obj: Type
): Type & PropEventSource<Type>;

const person = makeWatchedObject({ firstName: "Saoirse", age: 26 });

person.on("firstNameChanged", (newName) => {
  // newName은 string으로 추론됨 (firstName의 타입)
  console.log(newName.toUpperCase());
});

person.on("ageChanged", (newAge) => {
  // newAge는 number로 추론됨 (age의 타입)
  if (newAge < 0) console.warn("음수 나이");
});

// person.on("firstName", ...) // ❌ 컴파일 에러 - 패턴(`${Key}Changed`)에 맞지 않음
```

- `eventName: \`${Key}Changed\`` 자리에 `"ageChanged"`가 들어오면, TS가 역으로 `Key`를 `"age"`로 추론해서 `callback`의 인자 타입을 `Type["age"]`로 좁혀줌
- 문자열을 "파싱"하는 게 아니라 **패턴 매칭으로 타입 정보를 역산**하는 것에 가까움

<br>

#### 5. 키 리매핑 - 프로퍼티 이름 자체를 변형하기

---

- Mapped Type의 `as` 절에 템플릿 리터럴 타입을 쓰면, 순회하는 프로퍼티 **이름 자체를 다른 이름으로 바꿔서** 새 타입을 만들 수 있음
- 인터페이스의 모든 프로퍼티를 getter 메서드로 바꿔주는 `Getters<Type>` 예시

```typescript
type Getters<Type> = {
  [Property in keyof Type as `get${Capitalize<string & Property>}`]: () => Type[Property];
};

interface Person {
  name: string;
  age: number;
  location: string;
}

type LazyPerson = Getters<Person>;
// {
//   getName: () => string;
//   getAge: () => number;
//   getLocation: () => string;
// }
```

- `Property in keyof Type`으로 `"name" | "age" | "location"`을 순회하면서, `as` 절에서 각 이름을 `get${Capitalize<...>}` 패턴으로 다시 조립함
- `Property`는 `string | number | symbol` 타입이라 템플릿 리터럴에 바로 못 넣기 때문에 `string & Property`로 좁혀준 것 — 실무에서 이 조합을 자주 빼먹고 타입 에러를 만나게 됨

> 찰떡 비유: 우편물 재발송
>
> Mapped Type이 원래 주소(프로퍼티 이름)로 우편물(값)을 하나씩 배달하는 거라면, 키 리매핑은 배달 직전에 봉투 겉면의 주소만 다른 형식으로 다시 써 붙이는 것과 같음 — 내용물(값의 타입)은 그대로 두고 겉모습(키 이름)만 규칙적으로 바꿈

<br>

#### 6. 언제 쓰면 좋은가

---

- 후보 문자열이 유한하고 명확한 도메인에서 강력함
  - API 라우트 경로 (`` `/users/${number}` ``)
  - 이벤트 이름 규칙 (`` `on${Capitalize<string>}` ``)
  - CSS-in-JS의 단위 있는 값 (`` `${number}px` \| `${number}rem` ``)
  - i18n 키, 폼 필드 이름처럼 프로젝트 전역에서 네이밍 규칙을 강제하고 싶은 곳
- 반대로 자유 형식 문자열(사용자 입력, 파일 내용 등)에는 적합하지 않음 — 타입 레벨 정규식이 아니라 "정해진 패턴의 조합"만 표현할 수 있기 때문
- 조합 수가 큰 유니온을 여러 겹 곱하면 타입 체크 성능에 영향을 주므로, 실제로 필요한 만큼만 좁혀서 쓰는 게 좋음
